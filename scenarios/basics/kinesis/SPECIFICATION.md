# Amazon Kinesis Data Streams Specification

This specification describes a Basics scenario for Amazon Kinesis Data Streams that demonstrates how to create, configure, produce to, consume from, scale, and clean up a Kinesis data stream. The scenario tells a real-world story: a development team sets up a streaming data pipeline, ingests sensor telemetry records (both individually and in batches), reads those records back to verify delivery, inspects the stream's metadata and shard topology, scales capacity to handle higher throughput, and finally tears down all resources.

> **DRAFT** — This specification was generated by the Code Examples SpecGen AI tool. It should be reviewed for accuracy and correctness before implementation.

### Resources

No prerequisite resources from external AWS services are required. All resources (the Kinesis data stream itself) belong to the Kinesis service and are created and deleted using the Kinesis service client directly.

### API Actions Used

* [ListStreams](https://docs.aws.amazon.com/kinesis/latest/APIReference/API_ListStreams.html) — Lists available Kinesis data streams in the account.
* [CreateStream](https://docs.aws.amazon.com/kinesis/latest/APIReference/API_CreateStream.html) — Creates a new Kinesis data stream with a specified shard count.
* [DescribeStream](https://docs.aws.amazon.com/kinesis/latest/APIReference/API_DescribeStream.html) — Describes a stream including shard map and status (used to wait for ACTIVE status).
* [PutRecord](https://docs.aws.amazon.com/kinesis/latest/APIReference/API_PutRecord.html) — Writes a single data record to a stream.
* [PutRecords](https://docs.aws.amazon.com/kinesis/latest/APIReference/API_PutRecords.html) — Writes multiple data records to a stream in a single call.
* [GetShardIterator](https://docs.aws.amazon.com/kinesis/latest/APIReference/API_GetShardIterator.html) — Gets a shard iterator for reading records from a specific position in a shard.
* [GetRecords](https://docs.aws.amazon.com/kinesis/latest/APIReference/API_GetRecords.html) — Gets data records from a shard using a shard iterator.
* [DescribeStreamSummary](https://docs.aws.amazon.com/kinesis/latest/APIReference/API_DescribeStreamSummary.html) — Gets a summarized description of a stream including open shard count, retention, and encryption details.
* [UpdateShardCount](https://docs.aws.amazon.com/kinesis/latest/APIReference/API_UpdateShardCount.html) — Updates the shard count of a provisioned-mode stream (scale up or down).
* [DeleteStream](https://docs.aws.amazon.com/kinesis/latest/APIReference/API_DeleteStream.html) — Deletes a Kinesis data stream and all its shards and data.

## Hello Kinesis

The Hello example is a minimal, standalone runnable program that verifies connectivity to the Kinesis service.

1. Create a Kinesis service client.
2. Call `ListStreams` with no parameters (or a small `Limit` value such as 10).
3. Print each stream name returned in `StreamNames` and any `StreamSummaries` information (stream ARN, status, mode).
4. If `HasMoreStreams` is `true`, print a message indicating that additional streams exist.
5. If no streams exist, print a message saying no streams were found in the current region.

**Example output:**
```
Found 2 Kinesis data stream(s):
  - my-application-stream (ACTIVE, ON_DEMAND)
  - clickstream-prod (ACTIVE, PROVISIONED)
```

## Scenario

This scenario demonstrates a complete lifecycle of a Kinesis data stream: creation, data production (single and batch), data consumption, metadata inspection, capacity scaling, and cleanup. The stream uses **provisioned** capacity mode so that `UpdateShardCount` can be demonstrated.

The scenario generates a unique stream name (e.g., `sdk-example-stream-<random>`) to avoid conflicts.

### Setup

1. **List existing streams** — Call `ListStreams` to display any streams already in the account. This confirms connectivity and provides context.
   - Parameters: `Limit` = 10
   - Print stream names returned in `StreamNames`.

2. **Create a data stream** — Call `CreateStream` to create a new provisioned-mode Kinesis data stream.
   - Parameters:
     - `StreamName`: a generated unique name (e.g., `sdk-example-stream-<random-suffix>`)
     - `ShardCount`: 2
     - `StreamModeDetails`: `{ StreamMode: "PROVISIONED" }`
   - Print a message that the stream creation has been initiated.
   - `CreateStream` is asynchronous. The stream transitions from `CREATING` to `ACTIVE`.

3. **Wait for stream to become ACTIVE** — Poll `DescribeStream` in a loop until `StreamDescription.StreamStatus` equals `ACTIVE`.
   - Parameters: `StreamName` (the name from step 2)
   - Poll every 2-3 seconds, with a maximum of 60 seconds total wait time.
   - When ACTIVE, print the stream ARN, status, shard count (number of shards in the `Shards` array), and retention period.
   - If the stream does not become ACTIVE within the timeout, raise an error and proceed to cleanup.

### Produce: Write a single record

4. **Put a single record** — Call `PutRecord` to write one data record to the stream, simulating a single sensor reading.
   - Parameters:
     - `StreamName`: the stream name
     - `Data`: a JSON-encoded payload, e.g., `{"sensor_id": "sensor-1", "temperature": 22.5, "timestamp": "<ISO-8601>"}`
     - `PartitionKey`: `"sensor-1"`
   - Print the returned `ShardId` and `SequenceNumber` to confirm delivery.

### Produce: Write a batch of records

5. **Put multiple records** — Call `PutRecords` to write a batch of 5 records to the stream, simulating a burst of sensor telemetry.
   - Parameters:
     - `StreamName`: the stream name
     - `Records`: an array of 5 entries, each with:
       - `Data`: a JSON-encoded payload with varying sensor IDs and temperature values
       - `PartitionKey`: varied across 2-3 different sensor IDs to demonstrate distribution across shards
   - Print the `FailedRecordCount` from the response. For each record in the response `Records` array, print the `ShardId` and `SequenceNumber` (or `ErrorCode`/`ErrorMessage` if the record failed).
   - If `FailedRecordCount` > 0, retry the failed records (optional enhancement).

### Consume: Read records back

6. **Get a shard iterator** — Call `GetShardIterator` for one of the stream's shards to prepare for reading records.
   - Parameters:
     - `StreamName`: the stream name
     - `ShardId`: the first shard ID (e.g., `shardId-000000000000`, obtained from the `DescribeStream` response in step 3)
     - `ShardIteratorType`: `"TRIM_HORIZON"` (to read from the beginning of the shard)
   - Store the returned `ShardIterator`.

7. **Get records** — Call `GetRecords` using the shard iterator to retrieve the records that were written.
   - Parameters:
     - `ShardIterator`: the iterator from step 6
     - `Limit`: 10
   - Print each record's `PartitionKey`, decoded `Data` (base64-decoded), `SequenceNumber`, and `ApproximateArrivalTimestamp`.
   - Print `MillisBehindLatest` to show how close the consumer is to the tip of the stream.
   - Note: It may take a moment for records to be available. If the first call returns no records, wait 1 second and retry using `NextShardIterator` (up to 3 attempts).

### Inspect: Get stream metadata

8. **Describe stream summary** — Call `DescribeStreamSummary` to get a concise view of the stream's configuration.
   - Parameters: `StreamName` (the stream name)
   - Print key fields from the `StreamDescriptionSummary`:
     - `StreamName`, `StreamARN`, `StreamStatus`
     - `StreamModeDetails.StreamMode` (should be `PROVISIONED`)
     - `OpenShardCount`
     - `RetentionPeriodHours`
     - `StreamCreationTimestamp`
     - `EncryptionType`

### Scale: Update shard count

9. **Update shard count** — Call `UpdateShardCount` to scale the stream from 2 shards to 4 shards, demonstrating capacity management.
   - Parameters:
     - `StreamName`: the stream name
     - `TargetShardCount`: 4
     - `ScalingType`: `"UNIFORM_SCALING"`
   - Print the response showing `CurrentShardCount` and `TargetShardCount`.
   - Wait for the stream to return to `ACTIVE` status after scaling by polling `DescribeStream` (the stream goes to `UPDATING` during this process). Use the same polling logic as step 3, but allow up to 120 seconds for resharding to complete.
   - Once ACTIVE again, print a confirmation message showing the new shard count.

### Cleanup

10. **Delete the stream** — Call `DeleteStream` to remove the data stream and all its data.
    - Parameters:
      - `StreamName`: the stream name
      - `EnforceConsumerDeletion`: `true` (ensures any registered consumers are also removed)
    - Print a message confirming deletion was initiated.
    - Optionally poll `DescribeStream` until a `ResourceNotFoundException` is raised, confirming the stream is fully deleted. Alternatively, simply proceed after calling delete.

**Important:** The cleanup step must execute even if earlier steps fail. Implement a try/finally pattern (or language-equivalent) to ensure `DeleteStream` is always called if the stream was created.

### Outcome

When the scenario completes successfully, the user will have:
- Listed existing Kinesis data streams
- Created a new provisioned-mode data stream with 2 shards
- Written a single record to the stream
- Written a batch of 5 records to the stream
- Read records back from a shard, verifying data integrity
- Inspected the stream's summary metadata (mode, shard count, retention, encryption)
- Scaled the stream from 2 to 4 shards using UpdateShardCount
- Deleted the stream, leaving no orphaned resources

## Errors

Each action in the scenario should include basic exception handling. The table below specifies one primary exception per action to handle in the code.

| Action | Exception | Handling |
|-|-|-|
| `ListStreams` | `LimitExceededException` | Inform the user that the request rate was exceeded and suggest retrying after a brief delay. |
| `CreateStream` | `ResourceInUseException` | Notify the user that a stream with the specified name already exists. Offer to use the existing stream or choose a different name. |
| `DescribeStream` | `ResourceNotFoundException` | Notify the user that the specified stream does not exist. This may occur if the stream was not created successfully. |
| `PutRecord` | `ProvisionedThroughputExceededException` | Inform the user that the write throughput limit was exceeded. Suggest reducing the request rate or adding more shards. |
| `PutRecords` | `ProvisionedThroughputExceededException` | Inform the user that the batch write throughput limit was exceeded. Suggest splitting the batch into smaller requests or adding more shards. |
| `GetShardIterator` | `ResourceNotFoundException` | Notify the user that the specified stream or shard was not found. Verify stream name and shard ID. |
| `GetRecords` | `ExpiredIteratorException` | Inform the user that the shard iterator has expired (valid for 5 minutes). Obtain a new shard iterator and retry the read operation. |
| `DescribeStreamSummary` | `ResourceNotFoundException` | Notify the user that the specified stream does not exist or was already deleted. |
| `UpdateShardCount` | `ResourceInUseException` | Notify the user that the stream is not in ACTIVE state (it may be updating from a previous resharding). Wait for ACTIVE and retry. |
| `DeleteStream` | `ResourceNotFoundException` | The stream was already deleted or does not exist. Log the condition and continue cleanup without failing. |
